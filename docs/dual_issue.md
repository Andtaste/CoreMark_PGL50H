# 受限顺序双发：整核实现与物理验证

本轮状态为 `RESEARCH_COMPLETE_NOT_ADOPTED`。已经实现和验证真实双执行、双写回、双退休，
但**本轮三个候选均暂不建议采纳**：同频吞吐提升 4.230%，最高估计频率从 89.638 MHz
降至 83.942 MHz，按 IPC×Fmax 估计的吞吐仍下降 2.393%，资源增量也较大。
这不是用户已经明确拒绝的记录；生产单发版与已采纳状态保持不变。

完整比较见 [comparison.json](dual_issue/comparison.json)。本结论只针对本轮配对策略与实现，
不等于受限双发的性能上限。

## 实际实现的范围

槽 0 保留 RV32IM、访存、分支和 CSR；槽 1 只执行合法普通整数 ALU，
包括 LUI/AUIPC、OP-IMM 和非 M 的 OP。两个槽并行执行，没有槽 0 运算结果同拍串入槽 1。
分支/跳转、CSR/system/fence、除法单发；槽 0 的乘法可与槽 1 ALU 配对。

本轮主动采用的配对限制是：

- 只配同一个 8 字节对齐取指组中的连续两条指令，不跨组拼接。
- 同对 RAW 拆开发射；WAW 拆开发射；WAR 允许，旧操作数在 ID 捕获。
- 第二槽的已使用源寄存器只要存在活跃生产者就拆开，不区分生产者结果是否已经算出。
  第二槽不等待、不阻挡第一槽；随后该指令可以成为槽 0，使用普通转发。
- 第一条不得预测跳转，第二条不得命中 BTB。这样第二槽没有预测恢复或失效训练争用。
- 第一槽异常时，第二槽不退休；访存返回错误时，已经计算的第二槽结果也被丢弃。

这些是首版实现选择，会限制 IPC，并不是 ISA 或 FPGA 必须永久承担的限制。

取指接口扩为 64 位，每次读取对齐的两个字；PC 在上半字时只使用上半字。
四个组的队列最多容纳八条指令；命令和在途响应按组保留信用，不能把四个组等同于原八字队列的所有行为。
沿用同一 BTB64 内容、tag 和局部历史算法，以两个训练完全一致的副本提供两个查询口，
**容量仍是 64 个不同 PC，不是 128 项 BTB**。

RF 使用两个单写银行加 last-writer 位实现 4R2W，综合为分布式 RAM 的多读口副本。
WB 两槽同时写入不同的非零目的寄存器。八个 ledger token 改为描述有序退休组，
每组可有两个目的寄存器；依赖身份是 `{group_tag, lane}`，共四位。
第一槽操作数仍经过编码后的最年轻生产者选择和有 tag 的寄存转发。

第二槽结果随第一槽进入 EX/MEM、MEM 暂存和 WB，保持严格有序提交。
正常完成的组可以同拍退休两条；第一槽访存/乘法没有完成时，第二槽不能提前退休。
CSR `minstret`、统计总退休计数和 secondary 计数均支持同拍两条。
第二槽内部 trace 与第一槽同周期输出给研究测试台，退休轨迹按老到年轻排列后做差分。

本轮复用现有紫光 TDP RAM IP，以两份一致的完整 RAM 提供双字 IF 读取，
LSU 写入同时更新两个副本，并按八字节组保护跨端口读写碰撞。
FENCE.I、自修改代码和从 data RAM 取指仍受测试覆盖。
软件可见容量不变，但物理 DRM 从 48 增到 96；本轮尚未改为偶/奇字分银行存储。
IP 配置、初始化镜像和 PLL 均未修改，只增加实例。

## 同镜像性能

固定十次镜像 SHA256 为 `e9abfc84cbe4cf1402b4f2f17a035e5416751893dc98a261f06a914fdc2fb9ab`。
三个候选的全部 UART 指标、预测统计、乘法统计和实际发射/退休对数一致。

| 指标 | 当前采纳单发版 | 本轮双发三版 |
|---|---:|---:|
| 统计窗口周期 | 3,605,011 | 3,458,702 |
| 退休指令 | 2,808,261 | 2,808,261 |
| 精确 IPC | 0.778988 | 0.811941 |
| 同频吞吐提升 | — | +4.230% |
| 总周期减少 | — | 146,309（4.058%） |
| 软件计时周期 | 3,604,972 | 3,458,664 |
| 诊断 CoreMark/MHz | 2.773946 | 2.891289 |
| 第二槽退休 | 0 | 185,671 |
| 退休指令中参与配对的比例 | 0 | 13.223% |
| 预测下一 PC 错误 | 57,520 | 61,993 |
| EX 操作数等待 | 566,646 | 588,971 |
| ID blocked | 624,189 | 650,132 |
| MEM occupied 统计 | 71,640 | 65,160 |

参与配对的指令数是第二槽退休数的两倍。发射组数包含错误路径，不能与退休组数混用。
等待项彼此可能重叠，MEM occupied 也不是 RAM 响应延迟，不能相加反推程序周期。
更快消耗独立指令后，暴露的依赖等待可能增加；双发没有消除 load-use 依赖。

BTB 算法没换，但查询更早、组预取以及执行时刻改变了训练可见性；错误数多 4,473，
不能假定“同一 BTB”必然维持原预测统计。

另有**仅仿真对照**：保留宽取指与其它候选接口，强制禁止配对，
得到 3,622,899 周期、IPC 0.775142、61,992 次预测错误、第二槽退休零。
因此该实现的宽取指本身没有改善该负载；开启双发相对此对照少 164,197 周期，
相对原生产版净少 146,309 周期。对照没有做 PDS 或完整 ISA 回归，不能借用双发资源/频率。

固定一次验证镜像三个候选均为 347,184 个统计周期、280,944 条退休指令、
18,840 次第二槽退休，CRC 和独立窗口计数通过。单发原版为 361,883 周期。

实际配置仍为约 75 MHz，没有生成 bitstream 或上板；以上运行性能来自仿真。
CoreMark 镜像是固定短运行诊断版，不是正式合规 CoreMark 成绩。
固定镜像中 `No BTB` 页脚已过时，实际 `ENABLE_BP=1`。
该镜像打印 IPC 的边界仍假设 retired<=cycles，本次 CoreMark 满足此条件；
独立测试另验证了计数器在 IPC=2 和加二溢出时正确，未来高 IPC 软件打印需相应适配。

## 时序与资源

设备、约束、IP、镜像及 PDS 命令与基线一致。每个物理候选各一次完整 PDS，
没有新增 timing exception、降目标时钟或改变 PLL。

| 指标 | 单发基线 | 首版 | 队首更新收尾 | IF 静态预译码 |
|---|---:|---:|---:|---:|
| 估计 Fmax / MHz | 89.638 | 83.340 | 83.942 | 83.319 |
| 估计 IPC×Fmax 变化 | — | −3.093% | −2.393% | −3.117% |
| LUT | 6,461 | 9,057 | 9,156 | 9,206 |
| FF | 3,520 | 4,154 | 4,154 | 4,189 |
| Distributed RAM | 443 | 859 | 859 | 859 |
| DRM | 48 | 96 | 96 | 96 |

| Slow setup / ns | +2.177 | +1.334 | +1.420 | +1.331 |
| Slow hold / ns | +0.149 | +0.152 | +0.012 | +0.168 |
| Fast setup / ns | +5.432 | +4.775 | +4.881 | +4.887 |
| Fast hold / ns | +0.108 | +0.110 | +0.012 | +0.113 |

所有候选四角均零违例。频率最高版 hold 虽通过，但余量只有 12 ps，不能忽略。
维持本次 IPC 收益至少需要约 **86.000 MHz** 才能在估计 IPC×Fmax 上追平单发，三个候选都未达到。

Distributed RAM 增量主要与 RF 多读口复制、BTB 双查询和扩宽的结果队列有关，
不是额外插入了许多流水级；96 DRM 则来自完整 RAM 副本。
综合的 [RAM/APM 映射日志](dual_issue/dual_issue_predecode/pds/synthesize/apm_drm_lutram_utilization.log)
保存了推断组件，最终资源以 device map 表为准，不能把综合中组件行直接相加当作最终数量。

## 长链检查与三个候选的区别

**没有新增 MEM ready→EX→ID/FIFO 信用的组合反压链。**
ID/EX 与 EX/MEM 的输入信用仍只依赖寄存占用；RAM 返回仍终止于 WB；
两个执行槽之间没有同拍运算结果串联。第一槽访存请求授权仍在 MEM。

但这不表示“所有新控制路径都没有变长”。实际发现并尝试处理了前端配对回路：

1. 首版最差为 `head_inst → CSR/完整合法性 → pair_candidate → fetch head CE`，
   9 级逻辑、逻辑 2.924 ns、布线 8.142 ns，slack +1.334 ns。
   这确实是新增或加重的 ID→IF 控制回路，不能说完全没有跨模块长链。
2. 收尾版把队首更新 CE 与是否取两条分开，并用局部 opcode 译码判断第一槽合法性。
   最差转为第二槽完整译码→源依赖→配对→预测字段的数据选择：
   13 级、逻辑 4.383 ns、布线 7.132 ns，slack +1.420 ns。
   **仅把终点从 CE 换到 D 并没有消除问题。**
3. IF 预译码版把每条指令的静态配对资格、源使用位随取指响应一起寄存，
   ID 不再通过完整译码决定这些位；没有增加取指或执行拍。
   此版配对回前端的路径未进入列出的最差 30 条 slow setup 路径。
   最差改为 `rs2 → 最年轻生产者/槽号选择 → 入槽捕获转发 → operands.vb`，
   属于 ID 内部路径：10 级，逻辑 3.059 ns、布线 8.526 ns，源位 fanout 221。
   两个目的寄存器/组与新增转发来源使原 ID 路径更重；最终频率依然没有提高。

这说明预译码在结构上处理了前端回路的主要译码串联，但宽端口、tag 选择与布局成本仍存在。
不能用“路径终止于寄存器”或“最差终点变了”宣称时序问题全部解决。
完整路径分别保存在三个候选的 `slow_setup_paths.json` 和原始 `top.rtr`。

## 为什么配对率不高

在未修改 DUT 的观察仿真中，按实际 ID 接受的组做互斥划分，优先级从上到下：

| 首个不满足条件 | 发射组次数 | 占全部发射组 |
|---|---:|---:|
| 没有同组第二条 | 1,397,635 | 52.062% |
| 第一条类别不适合配对 | 128,973 | 4.804% |
| 预测资格不满足 | 278,919 | 10.390% |
| 第二条不是合法普通 ALU | 305,001 | 11.361% |
| 同对 RAW | 130,853 | 4.874% |
| 同对 WAW | 0 | 0 |
| 第二槽源存在较老活跃生产者 | 250,784 | 9.342% |
| 成功配对发射 | 192,419 | 7.168% |
| 合计 | 2,684,584 | 100% |

这些是**包含错误路径的发射组**，不是退休指令分布，也不是可节省周期。
第一项包含对齐组上半字单独使用、预测截断等情况，不能全归因为某一种原因。
条件顺序影响失败归类；例如预测资格失败可能同时不满足第二槽类别。
第二槽依赖限制连“已经算出、尚未退休”的生产者也会排除，仍有可研究空间，
但放宽它需要真实的数据可用与转发设计，不能直接把该计数当作潜在收益。

前两版辅助 `dependency_blocked` 计数为 592,934，预译码版为 298,727，
原因是非 ALU 的源使用位在静态资格中更早排除；它们不是同一失败统计口径。
上述互斥表才用于分析本轮配对限制。

## 功能验证与可复现性

三个物理候选各通过 10 组变延迟 core 测试、6 组 SoC 测试及 47 个继承 ISA 镜像。
随机 core/SoC 的两槽退休轨迹按顺序交给独立 RV32IM 解释器逐条核对。
异常、软件/定时器/外部中断、预测恢复、FENCE.I、自修改代码和访存背压由定向程序覆盖。

新增检查包括：

- RF 四读双写随机对照，以及前端随机背压/重定向/训练/flush，30,000 拍，
  240,000 次 RF 读取、8,176 次取指消费、1,256 次双字消费、233 次重定向、364 次旧响应排空。
- 同对 RAW、WAW、合法 WAR；主槽 load/store access fault 和未对齐 load 取消年轻结果。
  两种 core 延迟种子与 SoC 均通过，分别核对 trap PC/cause 与年轻寄存器没有提前改写。
- SoC 定向独立 ALU 流连续 **65 拍每拍退休两条**；主槽返回错误的第二槽取消实际命中两次。
- 总退休计数大于周期数、secondary 计数和加二溢出。
- 收尾版局部配对译码对完整译码器穷举 131,072 组；预译码版另检查同规模真值表及随机流中的资格位/指令归属。

对应首版/收尾版/预译码版分别为 68/69/70 项检查记录，另加各自两组固定 CoreMark。
测试覆盖不等同于正式 ISA 架构一致性认证。

入口为 `generate_dual_issue.py --variant dual_issue_finish`、`generate_dual_predecode.py`，
再用 `run_dual_predecode.py --phase smoke|checks|performance|validation` 和 `--extra`，
`check_dual_predecode.py`、`research_pds.py --variant dual_issue_predecode`。
前端单发对照见 `probe_dual_frontend.py`；原因观察器见 `profile_dual_issue.py`。
`archive_dual_issue.py` 核对来源、候选与原生产源/IP/镜像/STA，并生成归档 manifest。
首版旧生成工具与取指源保存在 `dual_issue/source_snapshot/`；复查首版应使用其保存的源与测试台。

建议保留为功能原型，下一步若继续应先收敛前端对齐/配对权限和端口存储组织，
再评估放宽第二槽数据来源。当前阶段直接扩大双发范围，容易继续放大 ID、转发和布线负担。
