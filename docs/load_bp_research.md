# Load 请求启动与分支预测研究

结论：确实有可减少周期的环节，但本轮直接实现的同频收益只有约 0.23%–1.22%，
已测候选的 PDS 估计频率损失更大。没有用这些研究副本替换已采纳核心。
生产 RTL、IP 配置、约束、镜像、采纳记录及原 STA 报告保持不变。

所有修改仅位于 `simulation/research/`、`simulation/results/load_bp_*/`，
归档在 `docs/load_bp_research/`。本研究不自动采纳任何候选。

## 基线与测量口径

基线是用户已采纳的 89.638 MHz、IPC 0.778988 版本。
另建独立 PDS 工作目录，使用相同器件、IP、约束、综合/布局布线选项，
重新得到相同的 89.638 MHz、6,461 LUT、3,520 FF、443 Distributed RAM、48 DRM、4 APM。
因此没有把生产目录中其他版本的 STA 拼接给研究候选。

全部周期对照使用固定的 CoreMark 10 次性能镜像，退休均为 2,808,261 条，
load/store/BJP 数量、种子和 CRC 一致。镜像 SHA256：
`e9abfc84cbe4cf1402b4f2f17a035e5416751893dc98a261f06a914fdc2fb9ab`。

“同频提速”由固定镜像的统计窗口周期计算；“估计峰值变化”再乘各自 PDS Fmax 比值，
不是板上性能。实际 PLL 仍约 75 MHz；所有列出的实现满足当前报告约束。
每个候选只进行了本轮一次 PDS 实现，不能把单次布局结果推断为架构的必然频率。

## Load：额外延迟到底来自哪里

仿真观察器按真实 EX 接受、队列位置和请求接受追踪各个 load 令牌，没有改变生产信号。

| EX 后接受请求的时间 | Load 数量 |
|---|---:|
| 1 拍 | 476,709（86.88%） |
| 2 拍 | 32,760 |
| 3 拍 | 39,240 |

请求接受到 WB 捕获仍全部是一拍。1 拍请求启动是当前 EX/MEM 寄存边界下的最早时刻。
超过这一拍的逐条 load 延迟总和为 111,240 拍，来源如下：

| 延迟来源 | 逐条 load 等待累计 |
|---|---:|
| 前方普通完成项正在推进，包括已完成乘法 | 53,800 |
| 前方乘法结果尚未就绪 | 13,320 |
| 前方 load/store 正在按顺序启动请求 | 44,120 |
| 当前 load 已在队首，但总线或响应阻塞它 | 0 |

这些是按每条 load 累积的等待量，可能包含同一时钟内多个 load，不能直接当作程序可节省周期。
此前的 211,089 拍“消费者等待 load 发请求”也包含必要的寄存边界时间，不能全部消除。

### 第二项 load 启动试验

观察到 20,120 次机会：MEM 空闲，队首是一条已完成、无异常的非访存指令，
第二项已经是一个注册在队列中的 load。可尝试让旧指令进入 WB，同时接受第二项 RAM load。

研究实现为队列第二项提供读取、一次消费两项：完成旧项并启动 load，
仍每拍最多一条 WB、一个未返回的数据事务；乘法必须完成才允许此路径，
仅对正常 RAM load 开启，故障与 kill 仍阻止年轻请求。
请求背压时保持两项，不提前移走旧项，保证已发布请求不变。
FIFO 入队信用仍只取注册占用，没有直接从 EX 发请求或让 RAM 返回进入 EX。

实际节省 16,520 拍，IPC 从 0.778988 到 0.782574，同频收益 0.460%。
虽然该观察机会当拍没有匹配的 EX 等待消费者，后续消费者仍会受益；
因此不能根据当拍等待计数为零断言此方案没有收益。

代价是新的第二项读取、请求选择和消费控制。最终 Fmax 86.919 MHz，
slow/fast hold 仅 +0.053/+0.036 ns；相对基线的估计峰值吞吐下降 2.587%。
本次综合并没有增加 Distributed RAM 计数，不能凭“多读口”直接宣称它增加了 RAM。
不过，同频收益偏小且频率/hold 不利，不建议直接采用这一版本。

试验初版在 Verilator 的性能镜像通过，但 Icarus 随机延迟测试停滞。
把第二项环形地址改为显式定宽的 `following` 指针后，两个环境重新验证通过。
初版源码与失败记录保存在 `lookahead_initial/`；它没有进入生产目录。

## 分支：真实冲突与重定向绕过分别计数

使用仿真影子元数据，随实际命令、在途响应、取指 FIFO、队首和发射令牌传递来源信息。
每次 EX 分支解析时核对保存的 hit 与影子状态一致，防止只按 PC 查询当前表项而误判历史。
记录同一窗口全部 571,070 次分支/跳转，并与原测试台方向/目标错误计数核对。

| 保存预测的来源 | 执行次数 | 方向错误 |
|---|---:|---:|
| 正常查表且 tag 命中 | 516,215 | 25,660 |
| 正常查表、有效槽但 tag 冲突 | 48,527 | 24,440 |
| 重定向请求绕过查表、保存顺序预测 | 6,327 | 3,717 |
| 查表槽无效 | 1 | 1 |

另有 3,702 次目标错误。热身后的窗口几乎没有真正的无效槽冷启动，
此前将全部 saved hit=0 看成容量冲突会高估冲突损失。

几个反复互相替换的真实槽位热点：

| 本次 PC ← 查表时占槽 PC | 次数 |
|---|---:|
| `0x6084 ← 0x5c84` | 5,120 |
| `0x5c84 ← 0x6084` | 5,100 |
| `0x5e9c ← 0x5c9c` | 4,320 |
| `0x5c9c ← 0x5e9c` | 4,300 |
| `0x5ef8 ← 0x5cf8` | 3,120 |

### 重定向目标查表

纠正 PC 已经过寄存器，但原 IF 为缩短局部路径，对纠正命令保存顺序预测。
实验让已寄存的纠正 PC 也查 BTB，用预测选择其后的 PC，不增加取指拍数。
FENCE flush 时仍禁止使用旧预测。没有把当前 EX 的原始分支结果组合接到 BTB。

基线 6,327 次绕过中，5,978 次对应 PC 在当时表内已有命中；
但不能据此声称这些都能避免误预测。实际仿真总错误从 57,520 降至 55,456，
减少 2,064 次、节省 8,256 拍，同频收益 0.230%。
最终 Fmax 为 84.602 MHz，估计峰值吞吐下降 5.402%，本版不建议直接采用。

### 保持 64 总项的两路 BTB

实验为 32 组、每组 2 路，仍总共 64 项；每项仍为 1 位已解析局部历史与两组 2 位计数器。
完整 tag 为 PC[31:7]，训练时命中原路，否则优先无效路，再按训练时 LRU 选择替换。
每组新增一个替换位，没有推测历史或跨级历史恢复。
还对比了组索引异或高位，以及与纠正目标查表组合。

两路直接索引将误预测降至 49,601；异或索引与纠正查表组合降至 46,659。
容量不变也能改善这些冲突，说明优化点不只是扩大表项数。
但新增查表/选择、替换状态与整体布局成本需要同时考虑。

## 后续优先级

1. 分支冲突是已被真实轨迹证实的优化点，优先级高于继续压榨第二项 load 启动。
   若继续，应以维持现有频率的冲突缓解/局部选择网络为目标；本轮两路实现仅作为研究起点。
2. 纠正目标再次遇到分支也有损失，但单独收益仅约 0.23%，值得为它接受的时序代价非常小。
3. Load 剩余启动延迟主要由顺序完成和单请求端口产生。没有发现一拍无用响应复制；
   不宜为了小于 0.5% 的收益引入更复杂的 MEM 控制，或重新打通 EX→RAM、RAM→EX。
4. 命中后的方向错误仍有 25,660 次。更复杂的方向预测可以继续研究，
   但此前局部历史长度筛选已说明“历史更长”不保证更好；本轮没有宣称解决这一部分。

## 验证范围与复现

- 各候选固定 10 次镜像 CRC、独立退休/事件计数通过。
- 两路异或组合、第二项 load 另通过固定 1 次验证镜像。
- 纠正查表、两路直接索引、两路异或组合及第二项 load 各通过 10 组随机延迟核心检查：
  directed、3 组随机程序和 prediction，各 2 个延迟种子；随机程序退休值由独立 RV32IM 解释器比较。
  directed 核对 10 次异常/中断原因，另有 SoC prediction/FENCE.I 自修改代码对照。
- 两路直接、两路异或各通过 20,000 次独立 BTB 模型更新，覆盖冲突替换、局部历史、无效化和 flush。
- 以上属于研究检查，不冒充完整 47 项 ISA 回归、正式采纳验证或板上结果。
- 全部实验结束后，生产源码、镜像、约束、IP 配置、采纳记录和原 STA 哈希仍与开始时一致。
