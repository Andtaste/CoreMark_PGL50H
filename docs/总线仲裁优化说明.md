# 总线仲裁优化：逐从设备仲裁

修改前基线已合并并推送到 main：e069717（2026-10-14）。它包含此前周期统计功能
和本地当前 CoreMark MAP。当前 test 工作区用于本次总线实验。

## 本次方案

第一版在 RIB 内为每个从设备独立仲裁：IF 访问 ram1 与数据访问 ram2/外设可以
同时获得访问权限。同一从设备只授予一个主设备，保持 JTAG > 数据 > IF 的优先级。
主从端口、地址高四位译码、从设备偏移地址、字节选择和现有 RAM/IP 都保留。

只修改两个硬件文件：

- hardware/pds/source/sys_bus/rib.v：独立生成每个从设备的候选请求与优先级选择，
  分别复用地址/写数据，向获得授权的主设备返回 ready/valid/读数据。
- hardware/pds/source/top/tinyriscv_soc_top.v：增加 PARALLEL_ACCESS 参数并传入 RIB。

```verilog
module tinyriscv_soc_top #(
    parameter PARALLEL_ACCESS = 1
)( /* 原有接口 */ );
```

PARALLEL_ACCESS=0：先在所有主设备中选择一个，再译码地址，与原全局仲裁一致。
PARALLEL_ACCESS=1：各从设备分别选择请求者；当前 SoC 默认启用。
RIB 模块自身的参数默认值为 0，由 SoC 显式传入模式。
参数在综合时确定，每次生成的 bitstream 只有选中的逻辑；不是运行时寄存器开关。

相比此前“取指直连 + ram1 新局部仲裁器”的草案，本次选择在现有 RIB 内实现并行，
以保持当前 IFU/EXU 依赖的时序。未新增 ram1_arb.v，因此 PDS 无需新增 RTL 源文件。
后续若需要独立预取或多未完成事务，再做请求/响应状态机和响应 owner 的整体改造。

## 协议边界

当前 IFU 使用 pc_prev 与 bus_switched 恢复取指，EXU 访存请求会持续保持，
store 写使能在现有完成阶段产生。第一版保持这些行为，未修改 ifu.v/exu_mem.v。
这是适配当前同步 RAM/外围设备协议的仲裁优化，不是 AXI 或通用可变延迟交叉开关。
返回路由沿用当前授权，不增加响应事务 owner；不能让主设备在旧响应未结束时
随意改变目标，也不能据此宣称支持任意响应延迟/乱序返回。
这些限制已存在于原总线接口；将来支持新的总线协议时需要一起修改请求者与从设备。

EX hold 仍会暂停前端，所以总线并行不会自动消除所有取指气泡。
优先比较总周期和 CRC；计数器变化用于解释结果，不能把各项直接求和。

## 无需上板的验证

新增可运行文件：

| 文件 | 用途 |
|---|---|
| [rib_arb_tb.v](../simulation/tb/unit/bus/rib_arb_tb.v) | 1003 组定向/随机仲裁检查，旧模式对照原 RIB，检查并行、优先级、地址/写掩码与返回路由 |
| [cpu_bus_soc_tb.v](../simulation/tb/soc/cpu_bus_soc_tb.v) | 当前 CPU/总线/外设组合仿真，检测 ISA PASS/FAIL、周期和并行授权 |
| [pds_ram_models.v](../simulation/models/memory/pds_ram_models.v) | 同步读、字节写和 RAM2 透明写的行为模型；不等同厂商时序仿真 |
| [ram2_parallel.S](../simulation/tests/bus/memory/ram2_parallel.S) | ram2 字/半字/字节写读、连续访存、load-use 与错误路径 store 检查 |
| [run_bus_regression.py](../simulation/scripts/run/run_bus_regression.py) | 编译和运行 unit、isa、data、coremark 或 all 套件 |

依赖 Python 3、Icarus Verilog 的 iverilog/vvp；data/coremark 套件还需 RISC-V GCC。
脚本接受 --iverilog、--vvp、--gcc 指定可执行程序，默认从 PATH 查找。
当前机器的 Python 可使用 Codex 捆绑运行时；Icarus 便携工具解压在 FPGA/tmp，
未安装到系统，未修改 PATH，未提交可执行程序。
工具来源：[FPGAwars/toolchain-iverilog v1.2.1](https://github.com/FPGAwars/toolchain-iverilog/releases/tag/v1.2.1)，
其 Windows 包中的 Icarus 版本为 10.2。不同机器请自行配置工具路径。

从工程根目录运行，例如：

```text
python simulation/scripts/run/run_bus_regression.py --suite unit
python simulation/scripts/run/run_bus_regression.py --suite isa
python simulation/scripts/run/run_bus_regression.py --suite data
python simulation/scripts/run/run_bus_regression.py --suite coremark
```

ISA 套件使用 references/tinyriscv/tests/isa/generated 中的 RV32I/M 夹具，
各用例在旧/新两种模式运行。unit 的原版 RIB 只在临时对照文件中分开共用循环变量 j，
防止 Icarus 组合块重复触发；仲裁等式不变，references 中的原文件没有修改。
原 PASS 宏先写 x26，再写 x27，TB 在结束标记之后等待流水线完成状态写入。
该协议只用于汇编夹具；C 程序可正常使用 x26/x27，CoreMark 的结束判定使用
链接后的 loop 符号地址，并在执行级确认出口自循环，避免把 C 临时寄存器值误当结束。

CoreMark 仿真单独编译 1 次迭代的烟雾测试程序，输出在忽略目录，
不覆盖 sw/coremark 的正式 ELF/BIN/DAT。为了缩短串口打印等待，TB 只在这一项
强制 UART 分频为 1，CPU/RAM/总线时序不加速。检查计算 CRC，短运行不是正式成绩。

输出：firmware/generated/bus_regression、results/logs/bus_regression、
results/reports/bus_regression_<suite>.json，均不提交。
测试覆盖不等于完整 ISA/特权规范验证；板上成绩仍需实际下载对比。

截至当前已完成：1003 组仲裁检查；47 个 RV32I/M 夹具在两种模式共 94 次均通过；
ram2_parallel 两种模式均通过，旧模式 1381 周期/0 次并行授权，
新模式 1273 周期/212 次并行授权。这里的周期含测试启动与结束检查。

CoreMark 1 次迭代仿真于 2026-10-14 达到 500000 个 CPU 周期后触发主机 600 秒
超时，尚未获得完整串口输出和 CRC。不是 TEST_TIMEOUT 或已确认的 RTL 错误，
但这项不能算通过；目前没有新方案的 CoreMark 周期改进数据。
RAM2 定向测试的收益不能直接换算成 CoreMark 的提升。核对 sw/link.lds 与
sw/coremark/coremark.map 后，当前代码运行于 ram1（0x00000000），运行时 .data、
.bss 与栈位于 ram2（0x10000000）。.data 的初始镜像保存在 ram1，由启动代码复制
到 ram2；不能把初始化镜像位置当成运行时数据位置。因此新仲裁可能改善 CoreMark
的取指/数据争用，实际收益仍需完整程序对照；IF 与数据访问同一从设备时仍然互斥。

## PDS 资源与时序实测（2026-10-14）

在 FPGA/tmp/pds_bus_compare/baseline 和 parallel 隔离目录分别执行 compile、
synthesize、dev_map、pnr、report_timing，未生成/下载 bitstream。
工具为 PDS 2022.2-SP1-Lite build 132640，器件 PGL50H-6 FBG484，
两次均使用原 tinydram.fdc 的 20 ns 时钟和默认实现设置、相同的 PLL/RAM IP。
旧版使用 e069717 的原始 RIB/SoC 顶层，新版使用当前逐从设备仲裁（模式 1）。

| 项目 | 旧版 | 新版 | 变化 |
|---|---:|---:|---:|
| LUT（布局布线后 top 汇总） | 5123 | 5241 | +118，约 +2.30% |
| FF | 3099 | 3100 | +1 |
| DRM | 48 | 48 | 0 |
| APM | 4 | 4 | 0 |
| PLL | 1 | 1 | 0 |
| CPU Setup WNS，Slow Corner | -0.131 ns | +1.317 ns | 本次新版满足 50 MHz |
| CPU Hold WHS，Slow Corner | +0.311 ns | +0.312 ns | 均满足 |
| CPU Hold WHS，Fast Corner | +0.242 ns | +0.242 ns | 均满足 |
| CPU 估计最高频率 | 49.675 MHz | 53.525 MHz | 单次实现估计值 |

新版 LUT 占器件 42800 LUT 的约 12.25%，FF 占 64200 FF 的约 4.83%；
48 DRM 占 134 DRM 的约 35.82%。资源增加较小，FF 差异来自综合结果；
仲裁 RTL 本身没有新增时序寄存器。频率差异包含布局布线变化，不能归因于总线逻辑
一项，也不能据此直接提高板上频率。当前约束对部分 UART/GPIO/JTAG 外部端口
没有输入/输出延迟，报告的 All Constraints Met 只覆盖已有约束。

原始 top.dmr、top.prr、top.rtr 和 run.tcl 另存于忽略目录
simulation/results/reports/pds_bus_compare/{baseline,parallel}/，可检查和重跑。
结论：现有验证支持“特定不同从设备访问有效、资源代价小、本次 50 MHz 内部时序满足”。
要确认 CoreMark 效果，仍需完整仿真或同程序 2000 次迭代的板上对照，检查 CRC、
Benchmark cycles64、IF 等待和 Memory stall；还需补充实际 JTAG 并发与复位交互测试。

再设为 1 重建下载，对比总周期、CRC、计数器和 Setup/Hold。

如果同时改了程序，再执行 BIN→DAT→Generate ram1 的原流程。
