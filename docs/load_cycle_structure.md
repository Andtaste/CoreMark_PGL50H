# Load-use 逐拍结构验证

本轮完成时序结构验证，状态为 **CYCLE_FEASIBILITY_ONLY**。没有接入候选 CPU，也没有修改已采纳 RTL、IP、约束、CoreMark 镜像或原 STA。结论：在地址和访存授权提前准备好的条件下，可以把相邻 load-use 的两个 EX 空泡减为一个；当前证据尚不足以决定把这一结构接入主核心。

后续已完成[隔离整核接入实验](early_load_integration.md)：少一拍在整核成立，但综合收益不足且新增控制链，候选未采纳。下文保留本轮逐拍验证的原始结论。

基准为 `docs/accepted_baseline.json` 中已采纳的 EX auxiliary 优化版本。固定 10 次 CoreMark 镜像 SHA256 为 `e9abfc84cbe4cf1402b4f2f17a035e5416751893dc98a261f06a914fdc2fb9ab`。

## 实际基准波形

用生产核心、生产总线和 Pango 同步 RAM 仿真模型运行定向程序，记录握手发生的时钟沿。E0 表示 load 从 EX 执行并进入 EX/MEM 队列的时钟沿，表内不是组合信号刚出现的时间。

| 操作 | ID 地址已准备的候选 | 当前核心实测 |
|---|---|---|
| ID 接收 load、提前地址寄存 | E−1 | E−1 只寄存操作数/指令 |
| load EX；RAM 请求被接受 | E0 | E0 地址入队 |
| RAM 返回数据进入 WB 寄存器 | E1 | E1 RAM 请求被接受 |
| 相关指令完成 EX | E2 | E2 返回数据进入 WB；E3 相关指令完成 EX |
| 两条指令之间 EX 空泡 | 1 | 2 |

生产核心的四组实测均符合 E0/E1/E2/E3：

| 定向操作 | load EX | 请求接受 | WB 捕获 | 消费者 EX |
|---|---:|---:|---:|---:|
| `lw → addi` | 24 | 25 | 26 | 27 |
| `lw → sw` 的写数据相关 | 40 | 41 | 42 | 43 |
| `lw → lw` 的基址相关 | 77 | 78 | 79 | 80 |
| 第二条 `lw → addi` | 80 | 81 | 82 | 83 |

退休结果也检查了数值和无异常。原始记录在 [directed/cycles.trace](load_cycle_structure/directed/cycles.trace)。

当前路径已经没有可直接删除的寄存复制拍。若仍在 E0 才算出并寄存地址，同步 RAM 最早 E1 接受请求；E2 捕获返回；E3 执行消费者。把返回数据同时写进操作数寄存器，也只能在 E3 执行，不能再省一拍。

## 条件成立时的局部验证

新增 [load_cycle_slice_tb.v](../simulation/research/load_cycle_slice_tb.v)，复用**未修改的生产 `nc_memory` 和 `nc_operands`**。基准通道在 EX 后寄存描述符；候选通道使用上一拍准备好的地址描述符。两个通道使用相同的一拍响应模型和 WB 寄存边界。

Icarus 和 Verilator 的逐拍结果一致，13 个用例通过：字、带符号字节/半字、无符号字节/半字；基址未提前准备时退回原路径；MMIO 退回；旧操作阻挡后放行；请求背压；未发布命令冲刷；已接受读取的响应失效；总线错误；非对齐本地异常。能提前且无背压的用例均为请求提前一拍、WB 提前一拍、消费者提前一拍。请求被背压时，省拍收益可能消失。

波形为 [slice.vcd](load_cycle_structure/slice.vcd)，两种仿真器日志和结果保存在同一目录。

这里的授权 `older_block` 是**外部接口假设**：授权来自已寄存的顺序信息，发布请求后必须维持其协议。该测试没有实现 CPU 全局授权，也没有证明整核精确异常。测试中的提前地址是输入；ID 的寄存器读口加法器延迟没有被测量。生产总线的跨端口读写碰撞保护仍需保留。已发布但未接受请求恰遇冲刷的整核协议，也必须在后续接入时单独验证，不能从局部用例推出正确性。

另重跑生产 MEM 的周转和随机交叠测试：128 轮加 16 次连续 load，共 208 请求/响应、47 次周转；随机测试 14,000 拍，6,126 次接受/完成、2,624 请求、185 次异常，均通过。这验证了现有 MEM 的接口能力，不代表提前请求已经接入 CPU。

## 当前执行轨迹中的覆盖机会

对生产 CoreMark 进行只读观察，没有向 DUT 写入信号。每条无基址依赖的 load 在 ID 用原始 RF 值计算影子地址，并在真实 EX 执行时断言地址一致。未将前递数据接进提前地址加法器。

| 条件，均基于当前未改变的执行轨迹 | load 数量 | 占全部 548,709 条 load |
|---|---:|---:|
| ID 时没有活跃基址生产者，可用原始 RF 备址 | 275,655 | 50.24% |
| 再要求所有旧指令退休、MEM/队列/WB 空闲、地址在 RAM 内 | 21,387 | 3.90% |
| 允许一条旧的无异常 ALU 队列项正常完成 | 25,737 | 4.69% |
| 队列空，允许复用 MEM 成功响应或缓冲项的周转 | 21,387 | 3.90% |

严格子集里，13,972 条 load 在后续确实阻挡过 EX 消费者；允许一条旧 ALU 的子集为 14,715 条。后者还需要在同一沿完成旧 ALU 并接受提前 load 的接口改动，局部早启动测试没有实现这个双动作接口。

**上述数量不是预测节省周期，也不是优化后的覆盖上限。** 提前一组请求可能改变后续总线占用；提前消费者也会改变 EX、队列和取指时序。因此不能用静态计数计算新 IPC，更不能把每条相关 load 都算作必省一拍。当前轨迹中放宽 MEM 周转没有增加机会，只能说明这类状态在这些时刻没有额外出现。

尤其是 `lw p,...; lw v,0(p)`：第二条 load 在 ID 尚无基址，第一版 RF 备址路径无法提前它。如果等前递值到达后立即做加法并直达 RAM，会重新形成“前递选择→地址加法→总线/RAM 控制”的链；再加一个地址寄存器则会用掉预期省下的一拍。

## 实现决策与剩余验证

本轮决定**保留结构研究，不直接改主核心**。从逐拍关系看，可以继续研究“ID 原始 RF 备址并寄存、合格 RAM load 早启动、其余退回”的隔离原型。但纯空闲条件的可见覆盖较低，不能仅凭局部省一拍就认为值得采纳。

接入前还需要完整设计请求所有权与顺序授权、队列旁路和 WB 冲突处理，并用整核仿真测量连续请求整体前移后的实际收益。必须保证基址等待、旧 store/旧异常、MMIO、分支恢复和背压都能正确退回，且 bus ready 不串回 ID 接收信用。物理实现还要检查新增 **ID RF 读口→地址加法→地址寄存器** 是否成为关键路径；本轮没有这项 STA 证据。

没有引入 RAM 返回直达 EX 的通路。候选的预期数据边界仍是“已寄存地址→同步 RAM→格式化→WB 寄存器→EX”，但是否避免整核长控制链，必须在完整 RTL 接入后再审查。

## 验证、资源与复现

只读 CoreMark 复跑仍为 **3,605,011 cycles，2,808,261 retired，IPC 0.778988**，CRC PASS，计数器独立核对 PASS。

本轮没有整核候选综合，不能给出候选资源或 Fmax。生产版本仍是 **Fmax 89.638 MHz，LUT 6461，FF 3520，Distributed RAM 443，DRM 48，APM 4**；实际 PLL 仍约 75 MHz。这些是原已采纳版本的数值。

运行 `python tools/check_load_cycles.py` 可复现。本轮来源、固定镜像、生成的测试平台、日志、逐拍波形与 [result.json](load_cycle_structure/result.json) 已归档，`manifest.json` 记录文件 SHA256。脚本在开始及结束检查已采纳源文件，并确认原生产 STA 和基准 JSON 未变。
