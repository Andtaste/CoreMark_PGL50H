## 2026-10-15：RAM 本地快速通路

### 目标和基线

基线为 `b9e184f`：五级顺序单发射 RV32IM/Zicsr、逐从设备 RIB、单端口 RAM1/RAM2。
目标是在保留软件和存储器布局的前提下缩短片内 RAM 通路，并减少访存请求启动的空拍。
本次按用户要求控制改动范围；已有功能验证完成后，清理阶段仅做必要的编译和引用检查。

### 实际结构

```text
IF ────────────────┬→ RAM1 本地仲裁 → 原 RAM1 IP
                   └→ RAM2 本地仲裁 → 原 RAM2 IP
LSU → 地址分流 ────┬→ RAM1/RAM2 本地仲裁
                   └→ 共享外设总线 → Timer / UART / GPIO
JTAG SBA ────────────→ 对应 RAM 仲裁或外设总线
```

- RAM1、RAM2 独立服务；同一 RAM 上优先级为 JTAG > LSU > IF。
- 外设共用一条请求／响应通路。响应目标及主设备归属在接受请求时保存，避免地址改变后串回其他请求者。
- 每个主设备及每个本地端口最多一项未完成事务；允许旧响应完成与新请求在同周期发生。
- ready 不依赖该主设备自身的 valid，减少前端消费信号沿取指请求再反馈的依赖。
- 片内 RAM 访问在 EX 完成合法性检查、且 MEM 可以前进后申请；接受请求与 EX→MEM 前进同时发生。
  仲裁失败时保留 EX，已接受请求不会在 MEM 重发；MMIO 继续在 MEM 发出。
- MEM 仍等待真实响应，不硬编码“下一拍必须返回”。保留原 load-use 互锁、转发、异常冲刷和中断排空。

### 实际改动及控制优先级

主改动限于 [ifu.v](../hardware/pds/source/core/ifu.v)。核心仅补充边界注释，保留原 ID 当拍冲刷门控。

```text
next_pc_q → cmd_pc_q/valid → 原取指接口 → pending_pc/fault/discard
                                                ↓ 响应
                                     4 项寄存 FIFO → ID → EX → MEM → WB
```

- FIFO 默认深度 4，每项 `{instruction32, PC32, fault2}`；参数 `FIFO_DEPTH` 仅控制深度。
  无空队列响应旁路。队列 payload 不整体复位，只复位指针、计数和有效控制。
- `next_pc_q` 在准备命令时递增；`cmd_pc_q` 保持未接受地址；`pending_pc` 保存已接受事务 PC。
  接受旧命令时可以同时准备下一条，响应返回与下条请求接受也可以同拍发生。
- 始终满足 `count + pending + cmd_valid <= FIFO_DEPTH`。
  准备命令只使用寄存占用量，不使用当拍 `ready_i/pop` 回收容量；接近满队列时允许保守空拍。
  从 prepared 到 pending、从 pending 到 FIFO 只转移预留，不重复占用。
- 对外请求不以 `flush_i/stop_i/id_fire` 组合门控。未接受请求保持 valid 和地址；
  单项 pending 只允许在空闲或旧响应到达时接受下一项。
- 跳转当拍核心继续阻止 ID→EX；IFU 在时钟沿清空队列并登记最新目标。
  已准备而未接受的命令以 `cmd_discard` 标记；已接受请求以 `discard` 标记。
  两者是粘滞状态，不通过单比特 epoch 翻转，以免连续跳转让旧事务重新有效。
- 跳转与接受同拍：新 pending 仍标记丢弃；跳转与响应同拍：旧响应不入队。
  旧命令即便随后被总线接受也只排空响应，不进入 ID。最新目标覆盖顺序 PC 更新。
- stop 禁止新命令准备，允许已准备／已接受事务继续完成；不丢失返回归属。
  非对齐或超出取指映射的地址生成带原 PC 的 fault 项，不发起真实总线访问。

这增加了取指响应到 ID 的寄存延迟，不再将 RAM 输出本身当作唯一 IF/ID 寄存。
仍为顺序单发射、EX/MEM/WB 结构不变；不能据“五级”名称推断跳转罚时完全不变。
预期代价是跳转恢复更慢；FIFO 不会自动降低分支密集程序的周期数。
没有加入旧前端开关、BTB、Cache、多项 outstanding 或额外总线拓扑。
BRAM 延迟适配、预测元数据和更深 FIFO 可沿现有边界扩展；双发射仍需另行设计。

### PDS 实现结果及取舍

同一工具、器件、原 PLL/IP、20 ns 约束下完成编译、综合、布局布线和时序分析：

| 指标 | RAM 快速通路基线 | 本次前端 | 变化 |
|---|---:|---:|---:|
| LUT，top 层次口径 | 4992 | 5012 | +20，+0.40% |
| FF | 3688 | 3593 | −95，−2.58% |
| Distributed RAM 单元 | 0 | 66 | 浅 FIFO 被推断为 LUTRAM |
| DRM / APM | 48 / 4 | 48 / 4 | 不变 |
| 50 MHz Setup WNS | +1.239 ns | +1.678 ns | +0.439 ns |
| Hold，慢角／快角 | +0.313 / +0.246 ns | +0.151 / +0.107 ns | 均满足 |
| 工具估计最高频率 | 53.302 MHz | 54.579 MHz | +2.40% |
| Latch | 0 | 0 | 不变 |

FIFO 的 payload 未强制复位，工具将其映射到 66 个分布式 RAM 单元，减少原队列使用的 FF；
因此实际并非“新增队列位数等于新增 FF 数量”。LUT 总数已经包含该 LUTRAM 用量，不能再相加。
四项队列很浅，本次没有为其额外占用 BRAM。这里的“寄存 FIFO”表示数据在时钟沿入队、
输出由队列状态控制，并不强制每一位必须映射为 FF。

当前最差路径为 `ex_inst[25] → EX 控制 → use_ex_request → local_ram_bus/p_ready[2] →
ex_ready → IF input bubbles 事件 → stat_count[2][29] 的 CE`，26 级逻辑，
逻辑 7.121 ns、布线 10.268 ns。最差端点已从 RAM1 地址变为统计计数器，但剩余 EX／仲裁控制仍很长。
本次未修改统计器或删减功能来改善时序。后续应根据该路径评估事件寄存和 EX／访存控制边界，
而不是继续单纯加深 FIFO。

此次建立了前端时序隔离边界，但 Fmax 增幅只有约 2.40%，两个定向程序周期增加约 4.5%；
这些数据不足以宣称总体性能或 CoreMark 得分提升。80 MHz 所需 12.5 ns 与当前估计 18.322 ns
仍相差约 5.822 ns。PLL 未改频，未生成／下载 bitstream，也未重跑 CoreMark。
基线物理指标来自清理无效源码前的默认拓扑；本次为清理后源码加前端改动的完整 PDS 实现，
单次实现差值也包含工具布局的变化，不将全部 0.439 ns 都归因于某一条逻辑删减。

## 2026-10-15：阶段控制拆分

### 基线、目标和分支清理

基线 `15e3ded`，工作分支 `codex/stage-control-split`。
根据上一轮 PDS 最差路径 `EX 编码／执行控制 → 仲裁 ready → ex_ready → 统计计数器 CE`，
将静态工作移到 ID/EX 边界，并将事件采样和计数分开。保留单发射及当前流水级数、
原 RAM 快速通路、软件和 PLL 配置；本轮没有引入新执行级、双核或浮点功能。

已确认 `abcd382` 同时是 `codex/five-stage-pipeline` 和当前分支的祖先，随后按用户要求
删除本地及远端 `codex/local-ram-fastpath`。提交由现有分支保留，不需要保留重复分支名称。

### 实施过程

1. 在 ID 进行只依赖指令位的合法性检查，寄存 `ex_illegal`；同时寄存 M 单元选择、
   串行指令标志、load/store 类别，共增加 5 个控制位。EX 继续检查有效地址对齐、地址范围和跳转目标。
   避免每拍从 EX opcode/funct7 经过全套异常结果选择再决定访存和完成条件。
2. 本地访存许可独立使用寄存类别／合法性、取指 fault 和有效地址检查。
   非访存分支／CSR 的异常结果不再串入 load/store 许可。非法或出错的 store 仍不能发出请求。
3. `ex_finished` 对 M 操作只依赖 M 完成／保存状态及取指 fault；其他指令直接完成。
   合法 M 指令没有地址或跳转异常，因此不需要让整个动态异常选择器进入这个完成信号。
4. CSR 增加 7 位 `stat_pending`，先采样合格事件，再驱动下一拍的饱和计数器。
   控制写周期仍不计数；停止在同一时钟沿排空最后一项事件；清零同时取消在途事件。
   运行中读自定义计数及 overflow 会滞后一拍，停止后最终窗口和 v1 地址／串口格式保持一致。
   `cycle/cycleh` 没有改变。软件现有“停止再读取”流程无需修改。
5. 首轮 PDS 得到 57.045 MHz、Setup +2.470 ns、5047 LUT、3605 FF。
   新最差路径是 `WB 相关比较／转发 → 地址检查 → 本地请求／仲裁 → ex_flush → IFU next_pc`。
   进一步利用已由指令类别和异常屏蔽保证的条件：
   `ex_redirect || ex_exception` 时 `ex_local_request==0`。
   将 `ex_flush` 写成 `ex_can_advance && (ex_redirect || ex_exception)`，
   等价于原 `ex_fire && (...)`，但不再依赖无关的访存仲裁 ready。
   load/store 的接受与 EX 前进仍使用原握手，未绕过真实访存响应。

没有保留两套实现开关。主要 RTL 修改仅为 `tinyriscv_core.v` 和 `csr_reg.v`。
本轮以现有 RTL 和实测路径为依据，没有声称复制或重新验证其他开源核心。
后续增加存储保护、Cache 错误等访存异常时，必须同步扩展 `ex_mem_fault` 的请求禁止条件，
继续维持“异常指令不发出本地访存请求”的约束。

## 2026-10-15：提前寄存转发控制与 ready 简化

### 基线与执行范围

先将当前完整项目 `8c72733` 快进到 `test` 并推送远端，再从该提交建立
`codex/forwarding-ready`。`test` 保存本轮改动前的项目。

随后用户授权“你直接仿真吧”，继续运行必要功能仿真和 PDS 实现。未上板。

### 改动一：独立提前寄存转发选择

主要文件：[tinyriscv_core.v](../hardware/pds/source/core/tinyriscv_core.v)。

旧路径每拍在 EX 比较 `mem_rd/wb_rd` 与 EX 源寄存器，再驱动操作数选择。
现增加 `ex_fwd_mem1/2`、`ex_fwd_wb1/2` 四个控制寄存位，EX 操作数选择使用这些位，
保留 x0 屏蔽、近端 MEM 非 load 优先、WB 转发和 load-use 互锁。

| 时钟沿前的状态 | 时钟沿后转发选择的计算 |
|---|---|
| ID 指令进入 EX | ID 源寄存器与当前 EX 目的寄存器比较，对应下一拍 MEM；与当前完成的 MEM 比较，对应下一拍 WB |
| EX 保持、MEM 未完成 | 保持 MEM 匹配，旧 WB 匹配不继续滞留；原 WB 数据通过 `ex_src1/2` 保存 |
| EX 保持、MEM 完成 | 对应匹配从 MEM 移到 WB，下一拍使用 WB 结果 |
| EX 前进且没有新 ID 指令 | 清除该消费者的选择有效位 |
| 复位／hard_flush | 清除全部转发选择 |

ID 接收时若原 EX 有效，`id_fire` 保证原 EX 同时前进，因此其生产者位置可以提前确定。
若 ID 在 EX 空闲但 MEM 等待时进入，只有实际完成的 MEM 才能成为下一拍 WB 来源。
这避免把当前 MEM/WB 的比较结果不加区分地延迟一拍。EX 保持时仍保存已转发操作数，
防止生产者写回退出后消费者失去正确数值。该关系也在后述程序中通过逐拍匹配断言核对，
并非覆盖所有输入组合的形式证明。

同时将 `ex_md_saved` 的数据捕获放入独立时序块，按 M 单元有效／完成条件保存。
`ex_md_done` 仍沿用原前进／暂停／冲刷优先级，决定保存结果能否使用；
正常完成并前进时额外捕获的内部数据不授权任何写回。
目标是让结果数据寄存使能不再经过全局 `id_fire` 优先级链。

### 改动二：简化请求 payload 与 ready 依赖

核心请求源改为：旧 MEM 请求存在时优先使用 MEM，否则提前呈现 EX 的地址、数据及访存宽度。
当实际请求有效时，仍按原来的 EX/MEM 归属输出；空闲时 payload 无效，不发出写操作。
不再用 `ex_local_request` 选择地址，去掉“EX 合法性／请求有效 → 地址 mux → ready”的间接反馈。

[local_ram_bus.v](../hardware/pds/source/sys_bus/local_ram_bus.v) 中，各主设备 ready 使用
自身地址译码得到的目标从设备 ready，结合原端口可用状态和仲裁优先级；
不再使用仲裁后 `p_addr[2]` 产生的共享外设 ready 反算主设备 ready。
物理端口接受和 owner 更新仍使用原 `p_req && p_ready`。

静态核对要点：某主设备 valid 且被允许接受时，它必然是该端口的仲裁胜者，
此时自身地址就是实际端口地址，所以自身 `target_ready` 与该端口 `p_ready` 一致。
JTAG > LSU > IF 优先级、响应 owner、同拍完成／接受和单次写入的控制仍保留。

**本轮是 ready 链的组合简化，不是将 ready 全部寄存。**
ready 仍依赖目标地址、端口占用、响应完成及高优先级竞争者；EX 本地访问仍按真实接受结果前进。
没有新建请求 FIFO、延迟一拍 ready、增加访存流水级或修改 BRAM 端口，
目标是在不主动增加访问延迟的前提下先减少冗余控制。
若后续 PDS 证明必须彻底隔离 ready，需再设计容量预留与请求缓冲，不能直接打一拍。

### 首轮时序回退及乘法控制边界修正

首轮 PDS 为 5029 LUT、3609 FF、Setup +2.213 ns、估计 56.221 MHz，
低于基线 58.997 MHz，因此不能将转发／ready 修改直接称为提频成功。
新最差路径是 `mie[7] → irq_pending/trap_start → M 单元操作使能／模式 →
DSP 级联 → 高位乘积符号修正 → mem_result`。
转发路径变化后布局及其他路径成为限制，不能凭一个最差端点断言所有其他路径都已满足 80 MHz。

检查发现 [exu_muldiv.v](../hardware/pds/source/core/exu_muldiv.v) 已寄存乘法操作数，
但符号预处理和结果选择仍由含当拍 `md_enable/hard_flush` 的操作信号控制。
将 2 位乘法类型与两个操作数同拍寄存，使乘法数据通路使用已寄存的模式；
握手、乘法延迟、除法状态机不变。模式会保留旧值，因此乘除结果改为在 `div_ready` 时选除法，
其余选择乘法结果，避免将旧乘积与除法结果按位 OR。
这是一处由实际报告触发的控制边界修正，没有增加新的乘法执行级或改写 DSP 算法。
